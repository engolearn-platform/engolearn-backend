# AI Companion request lifecycle

## Create and browse

The controller delegates to the feature service. The service reads the authenticated learner through `CurrentUserProvider`, and repository queries include that learner ID. Conversation pages use an encoded `(updatedAt,id)` cursor. Message history is loaded newest-first and reversed within the page so each page is chronological; a `beforeSequence` cursor selects older rows.

## Turn admission and streaming

1. The turn controller validates the request and synchronously calls `prepareTurn`. The service checks ownership and either atomically reserves capacity for a new turn and stores its user message, or claims the same pending user message for an explicit retry.
2. Before inference, the service asks Quota to check `AI_COMPANION_TOKEN_USAGE` availability against the learner's effective entitlement. This is a point-in-time check, not a reservation. Exhausted allowance or unavailable/missing policy fails closed before the stream begins. The daily window follows Quota's `Asia/Ho_Chi_Minh` calendar and the published policy; no token allowance is defined in Companion.
3. Initial prompt context combines the versioned persona, current CEFR level, recent history, and current input. Assessment results are not fetched or preloaded into this prompt. When needed, the app-controlled tool loop exposes the typed, read-only `getLatestAssessmentResult` tool, backed by Assessment's owner-scoped `AssessmentCompanionResults` contract. Tool arguments accept `detail` (`SUMMARY` or `SKILLS`, default `SUMMARY`) and optional `skillCodes` (up to five codes, valid with `SKILLS`). A summary returns official score, level, submission time and scope. `SKILLS` returns only rows visible to the learner: at most two for `PREVIEW` and five for `FULL`; supplied codes filter that visible subset, while omitting them returns all visible rows. No eligible result returns `NO_DATA`. The lookup excludes ineligible results and does not settle attempts or persist a newly observed grant.
4. Tool calls are sequential and bounded by configured call and round limits (default maximum five each). Spring-discovered handlers register their definitions and dispatch by tool name; duplicate names fail startup. Screen resolvers are a separate registry keyed by screen-context type. Unknown or malformed calls receive a safe tool result. Ordinary answer text is streamed as `delta`; provisional text is suppressed after tool-call frames. A provider failure may be retried once only before any delta reaches the client. After visible output, failure ends through the existing `error` event and the same turn ID/content can be explicitly retried.
5. Each successful model round must provide authoritative cumulative `totalTokenCount` metadata. Companion adds that total once for each successful round using checked arithmetic; it does not add prompt and completion counts on top of the total. Missing or invalid total usage fails safely: no assistant message, quota record, or `completed` event is committed, and the user message remains available for explicit retry.
6. After generation and usage validation, one Mongo transaction persists the final assistant message and calls Quota's `recordUsage` for the aggregate under the stable key `turn:<conversationId>:<turnId>`. `completed` is emitted only after this transaction commits. Quota records actual usage truthfully, including concurrent over-limit usage; availability is not a guarantee that a later record stays within the limit.
7. Provider failure, timeout, client disconnect, send failure, or task rejection releases the local reservation where possible. A Mongo lease and generation fence prevent stale workers from committing after their reservation expires. Cancellation is best effort at the provider; partial assistant output is never persisted.

## Context and provider

The initial prompt is composed from the versioned static core persona, the learner's current CEFR level, recent prior conversation messages, and the current input once. When an accepted turn has a screen reference, the registered resolver obtains a typed, owner-authorized Topic payload before inference, serializes it as bounded contextual data, and supplies it only for that turn. The current user text remains unchanged. The resolver uses the bounded executor and timeout; unavailable content fails the turn without model invocation. A retry loads the canonical reference and repeats authorization. Ordinary chat performs no screen lookup. See [Screen Awareness](screen-awareness.md). Assessment data is retrieved only on demand through the tool. The current input is excluded from history selection. History defaults to the newest 20 prior messages with a 4,000-token budget and is sent in chronological order. Tool results and provider continuation state are temporary request-time context, not persisted memory.

The Companion service uses EngoLearn-owned request, message, event, tool-call and tool-result types. Its continuation marker is opaque: the service passes it back unchanged, while the Gemini adapter alone interprets and stores the provider-native continuation in memory for the active turn. Continuations are not persisted, logged or exposed in SSE. The Gemini adapter contains the direct Google GenAI SDK integration. Neither Spring AI model classes nor Google GenAI SDK types cross the Companion model contract.

The Gemini adapter uses the configured model and temperature, caps output tokens, records only safe usage metadata, and maps provider failures to safe feature errors. It does not log prompts, message content, credentials, or raw provider errors.

Runtime settings use the `engolearn.ai-companion` prefix and environment overrides such as `AI_COMPANION_GEMINI_API_KEY`. Defaults are 100 visible messages, a 90% warning threshold, 20 history messages, a 4,000-token history budget, a 30-second inference timeout, a 90-second turn deadline, and up to 16 concurrent streams. The stream executor has no waiting queue; requests that exceed capacity receive a safe 503 response. Set a real API key only in the runtime environment; `.env.example` documents the variable without containing a credential.

## Deletion

Conversation deletion is owner-scoped and transactionally removes its messages with the parent conversation. It does not delete the learner's long-term memories.

## Memory retrieval and write flow

For each turn, the service retrieves eligible memories before model inference. Retrieval uses the configured embedding model (`gemini-embedding-2`; 768 dimensions) and the dedicated Qdrant collection, then resolves candidates against current owner-scoped Mongo records and their current versions. Only current records enter the prompt. Retrieved memory text and embeddings are transient request context; they are not written into conversation history or provider continuation state.

Automatic memory is effectively ON unless the learner explicitly stores OFF. Automatic create/update of any provenance must pass the setting fence at both admission and commit; an automatically saved directly shared fact may still use `source=EXPLICIT`. Every tool-proposed create/update requires an exact evidence excerpt from the current server-owned user input. The backend validates provenance and schema, not semantic equivalence; Gemini may propose a faithful paraphrase or conservative inference. An older turn cannot automatically recreate a memory forgotten after that turn was admitted: the turn's forget revision is checked at commit. Create/update require the model-classified trigger USER_REQUESTED or AUTOMATIC, distinct from source; the backend applies the setting fences for AUTOMATIC. Direct actions remain available when automatic memory is OFF, but the classification is not independently verified consent. Chat-based Forget retains its existing direct-request lexical guard. See [Memory proposal validation](memory-proposal-validation.md) for the design and residual risk.

Tool mutations use a server-assigned ordinal and normalized-argument fingerprint (including trigger for create/update). The mutation, current-turn/settings fences, and receipt commit atomically. A retry with the same turn and operation replays the receipt and stable `operationId`; changing arguments at the same ordinal returns `MEMORY_OPERATION_CONFLICT`. Provider tool-call IDs may change and do not define idempotency. Only the latest unanswered turn is retryable under the existing same-turn retry contract; no retry-after-reload or history backfill is supported. One retry maximum applies to a transient operation error; repeated failure returns the safe error outcome.

After Mongo commit, the service emits `memory_operation` with `operationId`, action (`CREATED`, `UPDATED`, or `DELETED`), `memoryId`, and `version`, then returns the tool result to the model. The event is independent of vector indexing and final assistant completion. No success event is sent for reads/searches, no-ops, validation rejection, or a pre-commit failure. Stream delivery is best effort; the durable effect and receipt do not roll back if the client disconnects.

## Vector synchronization and failure handling

Mongo remains authoritative if embedding or Qdrant work fails. A committed create/update is marked `PENDING`, then a single sequential worker consumes post-commit `(memoryId, version)` signals and polls pending rows. Successful upsert marks only the matching current version `SYNCED`; failures are marked `FAILED` and handled with at most one transient retry. The worker also consumes content-free deletion receipts. A stale worker cannot mark a newer memory version synced.

If embedding or Qdrant search is unavailable, retrieval fails open with only revalidated Mongo memories whose mode is `ALWAYS_ON`; there is no 503 and no claim that those records matched the current query. This does not make Qdrant authoritative or block canonical REST memory operations. On forget, the Mongo transaction removes the record and stores its point cleanup receipt before the API reports success. Retrieval hydrates and filters candidates against Mongo, so an old Qdrant point cannot return forgotten content. Failed deletion remains recoverable without retaining the content. An old conversation or replayed old turn cannot recreate it automatically.

The bounded manual reconciliation path is disabled by default. Enable it only for an operator-directed repair with `--engolearn.ai-companion.memory.reconcile-on-start=true`. It uses the same worker to page through live records for reindexing, process pending forgotten-point receipts, and scroll/delete orphan points in the dedicated collection. The memory settings prefix is `engolearn.ai-companion.memory`; supported tuning properties are `enabled`, `embedding-model`, `dimension`, `qdrant-url`, `collection`, `top-k`, `similarity-threshold`, `request-timeout`, `sync-batch-size`, `reconcile-on-start`, and `reconcile-page-limit`. See [vector recovery runbook](recovery.md) for procedure and verification.
